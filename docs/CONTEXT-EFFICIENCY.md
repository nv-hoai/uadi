# UADI Context Efficiency — Stage 0 baseline

**Status: Stage 0 audit, observational only.** This document defines how UADI measures context consumption and records the baseline that later stages must improve. It does not change the skill, the playbooks or the installer.

## 1. Principle: minimum sufficient context

Supply the minimum knowledge necessary for the agent to make its next high-quality decision.

Do not load knowledge merely because it exists. Do not remove knowledge merely because it consumes tokens. Optimize the complete outcome: quality, context, cost, speed and reliability.

A smaller skill that produces a materially worse interface is not an improvement. A skill that preserves quality while consuming fewer tokens, tool calls and dollars is.

## 2. Architecture under test

| Layer | Contents | Loading rule |
|---|---|---|
| **L0 Kernel** | Scope, priorities, task router, safeguards, loading budget | Always available; target 500–700 tokens after Stage 1 |
| **L1 Reasoning modules** | Product context; flow and states; content and consequences; visual composition; alternatives and trade-offs; accessibility review | Load only the modules that address a named design question |
| **L2 Specialist references** | Risk cards (billing, permissions, destructive actions, data freshness, health, ownership); patterns; schemas; examples | Retrieve only the relevant card, pattern or contract |
| **L3 Project memory** | Approved project constraints, decisions, rejected directions and open questions | Read from the host project's repository when relevant; target 400–700 tokens |

L3 is dynamic project state, not part of the static UADI installation. Approved entries are eligible for the compact memory brief; proposed entries are stored separately and never silently promoted; superseded entries remain for provenance but are excluded from active context.

## 3. What gets measured

Keep these separate rather than reporting one ambiguous "token" number:

| Measurement | Provenance |
|---|---|
| Files and sections read | Host/tool read events; wrapper events for probes |
| Repeated reads | Event aggregation |
| Provider input/output tokens | Provider usage metadata |
| Cached tokens and actual cost | Provider usage metadata |
| Peak context occupancy | Host telemetry, when available; never inferred from cumulative reads |
| Static token estimates | Explicitly labelled `chars/4` estimates |
| Module influence | Transcript and decision-trace evidence |

Every report carries an evidence tier:

- `instrumented` — host or tool read events.
- `wrapper` — reads recorded through `scripts/context-read.mjs`.
- `mixed` — more than one event source.
- `self_reported` — agent-written, format-validated only.

Generated by `npm run context:report` on 2026-11-08. Token values are `chars/4` estimates, not tokenizer or provider output.

| Core (`docs/DESIGN-INTELLIGENCE.md`) | 1 | 873 | 1,000 | within |
| Always (kernel + core) | 2 | 2,131 | 2,300 | within |
| Typical (always + four playbooks) | 6 | 14,912 | 16,000 | within current, far above target |

The key distinction: **installed is not loaded.** The installer currently ships 55 files, 325,946 bytes and 40,673 words. An agent that reads only the kernel and core consumes ~2,131 estimated tokens; one that follows the current "read core, then load methods" path and reads all four playbooks reaches ~14,912; adding accessibility, quality gates and a pattern reaches ~20,200. None of those numbers is a measured provider token count.

`npm run context:report -- --check` currently exits non-zero because the kernel is 58 estimated tokens over its 1,200 budget. That is a Stage 1 finding, not a regression introduced by this audit.

## 5. What the baseline does not show

- It does not show which files a real agent read. The historical confirmatory `transcript.md` files are placeholders ("Record the complete transcript here"), and `tokens.json` records only an output-size estimate. Historical read events cannot be reconstructed.
- It does not show peak context occupancy, cached tokens or billed cost.
- It does not show whether a loaded module changed a design decision.
- It does not establish that any profile is better; it establishes the starting point.

## 6. Smoke test

The smoke test uses `scripts/context-read.mjs` to record machine-readable read events for representative task classes. It is a probe of the instrumentation and the current loading path, not a quality evaluation.

Protocol:

1. Run two or three representative task classes (small, medium, complex) in separate sessions.
2. Read UADI guidance through the wrapper, not the host's normal read tool, so events are captured.
3. Validate the log with `npm run context:validate -- --log <file> --check-paths`.
4. Record the generated Markdown report under `benchmarks/context-smoke/` and state the evidence tier.

Results are recorded in [`benchmarks/context-smoke/README.md`](../benchmarks/context-smoke/README.md). If a session cannot use the wrapper, the log is labelled `self_reported` and cannot support an instrumented claim.

Two wrapper probes (medium subscription settings, complex onboarding) recorded six reads each: **9,597** and **10,372** estimated tokens. The kernel + core baseline was 2,131 in both; the monolithic UX Reasoning playbook alone was 5,405, 56% of the medium load and 52% of the complex load. Pattern reads were selective, and no repeated reads occurred. The evidence tier is `wrapper`, not natural host telemetry, so these numbers are a probe rather than a baseline distribution.

## 7. Stage 0 exit gates

- `npm run context:report` produces the static inventory and profile estimates.
- `npm run context:validate -- --log <file>` validates and summarises an event log.
- The smoke test records read events, detects repeated reads and labels its evidence tier.
- `npm test` passes; the new scripts have unit tests.
- No changes to `SKILL.md`, playbooks, `install-skill.mjs` or benchmark execution.

## 8. Consequences for later stages

- **Stage 1:** kernel ≤700 tokens; move billing-specific rules out of the always-on entry point; validate every router target.
- **Stage 2:** split/distill the four playbooks into six coherent reasoning modules; one authoritative operational source; risk cards loaded only on trigger.
- **Stage 3:** `standard` default; `compact` and `extended` profiles; installer checks that every route exists in the selected profile.
- **Stage 4:** B/C non-inferiority with a pre-registered quality margin (lower 95% bound not below −2 points), then measured context/cost/time reduction.
- **Stage 5:** separate C/A cross-domain evaluation; do not mix retention and advantage claims.
