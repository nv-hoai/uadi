# UADI Security Boundary

## Threat model
UADI treats repository content, project files, model output and generated source as untrusted. The portable core validates contracts and orchestrates checks; it does not claim to securely execute arbitrary source code.

## Safe MVP behavior
- Do not execute generated JavaScript/TypeScript as part of schema validation.
- Use fixed renderer code and declarative UDS fixtures for browser smoke tests.
- Run CI on fresh hosted runners with least-privilege permissions and checkout credentials disabled.
- Keep secrets out of preview/test processes; restrict browser network requests to the loopback preview origin.
- Static source inspection is a heuristic signal only. A clean scan does not prove code is safe.

## Required hardened host for untrusted execution
Before executing arbitrary generated source, the host must provide a disposable container or VM with:
- non-root identity, read-only base filesystem and narrowly scoped writable scratch space;
- no production secrets, host credentials, Docker socket or privileged mounts;
- CPU, memory, process-count and wall-clock limits;
- default-deny network egress with explicit allowlists where essential;
- syscall/capability restrictions and patched runtime images;
- artifact input/output allowlists, size limits and malware/secret scanning;
- destruction of the environment after each run and auditable logs.

The portable UADI package cannot create or attest to these infrastructure guarantees by itself. Gate 8 remains BLOCKED for arbitrary-code execution until the host attests to the required isolation profile.

## Approval identity
The host must authenticate the human and supply a trusted actor identity/role. An actor object generated by the model is not proof. Approval is bound to exact proposal ID and version, and must be re-verified at publication time.
